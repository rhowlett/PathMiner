# ADR-010: Compiled-Acceleration Deferral and Solver-Backend Thresholds

**Status:** Accepted
**Date:** 2026-09-04
**Context:** Session 04 — Geometry and numerical backend extraction
**Decision Makers:** PathMiner project team
**Closes:** BASE-005 ("Defer a C/C++ rewrite until profiling justifies it")
**Related:** ADR-001 (parity policy), ADR-003 (SciPy optional; pure-Python fallback required),
ARCH-006 (one solver dispatcher), ARCH-007 (factorization reuse), QA-006 (performance budgets)

---

## Context

PathMiner's two-terminal resistance is computed by nodal analysis: ground the
source, inject 1 A at the sink, and read the sink potential. v0.13 ships three
numerical backends for this single problem, now extracted into
`pathminer/core/solver.py` (Session 04) with numerical behavior preserved:

- **Dense** — Gauss-Jordan with partial pivoting (`solve_dense`). O(n³) but
  trivial for the tens-of-nodes graphs produced by point-to-point and ladder
  models.
- **Pure-Python sparse** — Jacobi-preconditioned conjugate gradient on the
  grounded Laplacian (`solve_cg`). Always available, including inside a
  KiCad-bundled Python interpreter that has no scientific stack.
- **Optional compiled sparse** — SciPy's `spsolve` (`solve_scipy`), two to
  three orders of magnitude faster than the Python CG on meshed pours, used
  opportunistically when SciPy is installed.

BASE-005 asks whether PathMiner should invest in a C/C++ rewrite of the solver
and, if not yet, to **document the decision and the performance thresholds** at
which compiled acceleration would be introduced. This ADR records that
decision and those thresholds so later sessions do not re-litigate it ad hoc.

---

## Problem Statement

A premature C/C++ (or Cython/Rust) rewrite of the solver would:

- Add a native build/toolchain to every install target, including the
  KiCad-plugin path where a compiled extension may not load at all.
- Fork numerical behavior away from the validated pure-Python vectors before
  the architecture (graph reuse, factorization reuse, model selection) has
  stabilized.
- Optimize a component that has not been shown by profiling to dominate
  end-to-end runtime.

Conversely, forbidding compiled acceleration forever would leave large meshed
pours slow on machines without SciPy. The project needs a **bounded, testable
rule**, not a permanent ban.

---

## Decision

**Defer any compiled (C/C++/Cython/Rust) solver rewrite. Optimize graph reuse
and sparse factorization first, keep the pure-Python solver as a always-present
fallback, and adopt SciPy opportunistically — all behind one stable dispatcher
with asserted backend agreement.**

1. **One dispatcher, backend-independent (ARCH-006).**
   `two_terminal_resistance(edges, src, dst, backend="auto", dense_limit=…)`
   is the single entry point. It accepts a backend-neutral edge list and
   returns the same resistance regardless of backend. The three backends are
   asserted to agree on the same networks (V11/V20 vectors in
   `tests/test_solver.py`).

2. **Pure-Python fallback is mandatory (ADR-003).** `solve_cg` has no
   third-party dependency and must remain a supported backend so PathMiner runs
   in a bare KiCad interpreter. SciPy is an accelerator, never a requirement.

3. **Selection thresholds (the crux of BASE-005) — documented and codified:**

   | Threshold | Value | Meaning |
   |---|---|---|
   | `DENSE_NODE_LIMIT` | **400 nodes** | At or below this node count, `backend="auto"` uses the dense Gauss-Jordan solve. Above it, the network uses the sparse path. Reproduces v0.13's `network_resistance` crossover. |
   | Sparse backend preference | **SciPy if `HAVE_SCIPY` else CG** | On the sparse path, the compiled SciPy `spsolve` is used when installed; otherwise the pure-Python CG. |
   | CG convergence | `tol = 1e-13`, `maxit = 50000` | v0.13 conjugate-gradient stopping criteria, preserved. |
   | Cost model | `t = a · nodes^b`, `b ∈ [0.8, 3.0]` | `calibrate_solver()` learns `a`, `b` from two synthetic grids on the running machine; `estimate_seconds(nodes)` forecasts per-solve time. This is the profiling hook. |

4. **Optimization order before any compiled work.** In priority order:
   (a) reuse graph construction and factorization across terminal pairs
   (ARCH-007, Session 13) — the largest expected win, since batch runtime is
   dominated by repeated builds, not the solve itself; (b) opportunistic SciPy
   (already available); (c) *only then*, if still justified, compiled
   acceleration.

5. **Compiled acceleration is introduced only behind the stable solver API,
   after profiling proves the need.** A future compiled backend must plug in as
   another `backend=…` value behind `two_terminal_resistance`, keep the
   pure-Python fallback, and pass the same backend-agreement vectors.

6. **Backend agreement means agreement on failure, not only on value.** Every
   edge-list backend routes through one shared validation/component helper
   (`pathminer.core.solver._prepare`), so dense, CG, SciPy, and `auto` accept
   and reject exactly the same inputs. This is required for ADR-001 parity: a
   backend that returned a plausible-but-wrong number where another raised
   would silently fork behavior.

## Backend Consistency and Input Validation (Session 04 review repair)

Coordinator review of the first Session 04 cut (status `CHANGES_REQUESTED`)
found the three backends inherited an inconsistency from v0.13: `_solve_scipy`
validated its inputs and restricted the solve to the source's connected
component, but `solve_cg` did neither — it returned the last iterate for a
disconnected or non-converged system — and the dense `network_resistance` path
raised a bare `singular network matrix` (or `KeyError`) on unrelated
components, `src == dst`, or a missing endpoint. Three backends could therefore
disagree on whether a network was even solvable.

The repair lifts SciPy's discipline into the shared `_prepare`, used by all
three backends and the `auto` dispatcher, plus a convergence guard on CG. The
result is one behavior table for every backend:

| Condition | Behavior (all backends) | Named error |
|---|---|---|
| Valid connected network | Same resistance, v0.13 numerics preserved | — |
| Unrelated (disconnected) component present, `src`↔`dst` still connected | Solved over `src`'s component; stray island ignored | — |
| Non-positive resistance (`r <= 0`) on a real edge | Rejected | `ValueError("non-positive resistance in network")` |
| Self-loop (`u == v`) | Edge dropped (v0.13 behavior) | — |
| Non-finite resistance (`NaN`/`±inf`) | Rejected | `ValueError("non-finite resistance in network")` |
| Endpoint absent from every edge | Rejected | `ValueError("endpoint not in graph")` |
| `src == dst` | Rejected | `ValueError("source and sink are the same node")` |
| `dst` not in `src`'s component | Rejected | `ValueError("endpoints are not connected")` |
| CG residual never reaches `tol` within `maxit` | Rejected (never returns the iterate) | `ValueError("conjugate-gradient solve did not converge")` |

**Parity is unaffected.** For a valid connected network the component *is* the
whole graph, so `_prepare` changes neither the node set nor its
`sorted(…, key=str)` ordering; CG and SciPy remain bit-identical (`==`) to
their v0.13 originals and the dense dispatcher stays within 1e-12 of v0.13
`network_resistance` (verified on the V11/V20 vectors). Only the previously
undefined or backend-divergent cases change, and they change toward a single,
loud, shared failure. Non-finite (`NaN`/`±inf`) and non-positive (`r <= 0`)
resistances are inputs v0.13 tolerated — non-finite via `1/NaN` on the dense
path or a silent drop on the sparse path, and non-positive by dropping the edge
on every path — that are now rejected with a named error on every backend
(coordinator review correction). Carrying an "open" connection as `inf` or a
"short" as `0` is not supported — omit the edge or merge the two nodes instead.
Self-loops (`u == v`) remain dropped, unchanged.

## Trigger Criteria — When to Revisit Compiled Acceleration

Compiled acceleration is reconsidered only when **all** of the following hold,
with evidence recorded in a superseding ADR:

1. **Profiling** (`calibrate_solver`/`estimate_seconds` plus the QA-006
   performance benchmarks) shows the *solve step* — not graph construction,
   parsing, or reporting — dominates end-to-end runtime on representative
   boards (e.g. the IP5385 real-board suite and large ground nets).
2. **Factorization/graph reuse (ARCH-007) is already in place** and the solve
   still exceeds the QA-006 batch-solve or mesh-solve performance budget.
3. **SciPy is unavailable or insufficient** on a required target — most
   plausibly the KiCad-bundled interpreter — so the pure-Python CG is the only
   fallback and misses the budget there.

Absent all three, the decision stands: no compiled rewrite.

---

## Rationale: Why Not Rewrite Now?

| Approach | Pros | Cons | Verdict |
|---|---|---|---|
| **Compiled rewrite now** | Fastest large-mesh solve | Native toolchain per target; plugin may not load it; forks validated numerics; optimizes an unprofiled component | ✗ Premature |
| **Ban compiled forever** | Simplest packaging | Leaves SciPy-less machines slow on big meshes with no escape hatch | ✗ Too rigid |
| **Defer behind stable API + thresholds** | Working, portable solver today; SciPy speed when present; clear, testable trigger to revisit; numerics stay validated | Large SciPy-less meshes remain CG-bound until a trigger fires | ✓ Best fit |

---

## Consequences

| Consequence | Severity | Mitigation |
|---|---|---|
| SciPy-less machines are CG-bound on very large meshed pours | Medium | Opportunistic SciPy; ARCH-007 reuse; documented trigger to revisit |
| Two sparse code paths (CG and SciPy) to keep in agreement | Low | Backend-agreement vectors (V11/V20) assert identical results |
| `DENSE_NODE_LIMIT` is a heuristic crossover, not per-machine tuned | Low | Overridable per call via `dense_limit`; calibration forecasts cost |
| Decision must be revisited, not assumed permanent | Low | Explicit trigger criteria and a superseding-ADR requirement |

---

## Parity Note

This ADR documents a decision and thresholds; it introduces **no** numerical
change. The extracted backends reproduce v0.13 results bit-for-bit
(`solve_cg`, `solve_scipy`, `solve_dense`) or within solver precision (the
dense dispatcher vs. v0.13 `network_resistance`), verified in
`tests/test_solver.py` against the original V11/V14/V20 acceptance vectors.
