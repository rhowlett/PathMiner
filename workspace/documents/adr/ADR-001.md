# ADR-001: Incremental Refactor and Parity Policy

**Status:** Accepted  
**Date:** 2026-08-26  
**Context:** Session 01 baseline freeze  
**Decision Makers:** PathMiner project team  

---

## Context

PathMiner v0.13 is a validated, working single-file application (5545 lines) with:
- Proven numerical correctness: 656/656 acceptance vectors passing
- Established user workflows: GUI (Trace, Via/Path, Stackup, Report tabs) and CLI
- Published material models and engineering guarantees
- Actual use in field verification and board design review

The application will be refactored into a maintainable, layered package structure to enable:
1. Incremental capability expansion (multi-net power paths, DC return, thermal, signal integrity)
2. Multiple delivery forms (GUI, CLI, KiCad plugin, automation library)
3. Testable architecture with enforced layer boundaries
4. Vendor-independent headless engine

However, the refactor spans many months and many developers. We must ensure that:
- Every intermediate milestone remains a runnable, passing application
- No regression in numerical accuracy or user workflows occurs silently
- The validated v0.13 models and results are never lost
- The engineering team can use the product at every stage

---

## Problem Statement

A "big-bang" rewrite risks:
- Lost regression coverage (tests lagging behind changes)
- Silent numerical regressions (only detected in the field)
- Broken user workflows mid-project
- Abandonment of v0.13 (cannot backport fixes)
- No "last known good" to fall back to
- Inability to correlate issues to a specific refactor stage

A pure "copy-paste split" risks:
- Duplicated formulas (divergence over time)
- Inconsistent state between GUI and CLI
- Fragmented test suites (different coverage per layer)
- Ad-hoc schema evolution
- Unclear ownership and dependency direction

---

## Decision

**Adopt incremental refactoring with locked parity gates.**

Every session:
1. **Preserves a working milestone.** The application runs and passes all acceptance tests before and after the session's changes.
2. **Maintains numerical equivalence.** v0.13 results are reproduced within published tolerances or explicitly authorized changes are documented.
3. **Extracts one logical layer.** Sessions proceed in order through units, materials, geometry, network, analysis, reporting, and UI.
4. **Retains stable APIs.** CLI commands, GUI behaviors, JSON schemas, and report formats remain compatible unless session-explicitly authorized to change.
5. **Consolidates formulas early.** Shared business logic is moved to owned modules and tested independently before being adopted by GUI and CLI.
6. **Tests at every layer.** Unit tests for models, integration tests for headless engine, acceptance tests for CLI/GUI.

---

## Mechanical Extraction Precedes Behavior Change

The refactor follows this sequence:

1. **M0 (Baseline):** Freeze and test v0.13, measure performance baselines.
2. **M1 (Package split):** Extract code into modules (core, kicad, analysis, report, cli, ui) without changing behavior. All v0.13 tests pass.
3. **M2 (Contracts):** Define shared data types (ProjectContext, SelectionModel, AnalysisResult). Implement versioned schemas and storage. Tests pass.
4. **M3 (Headless):** Move analysis out of widgets into a standalone runner. Implement report registry and new CLI subcommands. Tests pass.
5. **M4 (UI redesign):** Rebuild GUI to use shared contracts (Project / Investigation / Analysis / Reports / Diagnostics). Tests pass.
6. **R1 (Release):** Stabilize and document Resistance v1. Feature-complete, regression-ready.

*Then* capability expansion (system power, DC return, thermal, signal return) proceeds with its own parity gates.

---

## Rationale: Why Not Rewrite?

| Approach | Pros | Cons | Verdict |
|----------|------|------|---------|
| **Big-bang rewrite** | Fresh design, clean code | Months with no working app; regression silent until deployed; old code abandoned | ✗ Too risky for validated product |
| **Pure copy-paste split** | Fast initial extraction | Duplicated formulas; inconsistent state; no enforced layer boundaries; hard to refactor later | ✗ Creates tech debt immediately |
| **Incremental parity gates** | Working app at every step; regressions caught immediately; formulas consolidated early; clear layer boundaries | Slower initial progress; discipline required; each session must fit within scope | ✓ Best for validated product |

---

## Parity Definition

**Numerical Parity:** All v0.13 acceptance vectors produce the same results (IEEE-754 exact match or within published tolerance if rounding changes).

**API Parity:** Every v0.13 CLI command, option, and default remains available with the same syntax and behavior.

**Schema Parity:** v0.13 net-selection files load without loss; schema may be extended but must not break existing files.

**UI Parity:** v0.13 workflows (manual trace, board trace, pair selection, report generation) remain possible with the same user steps.

**Performance Parity:** Project load, interactive response, and batch solve times do not regress by more than 10% without explicit authorization.

---

## Enforcement Mechanisms

1. **Locked acceptance tests.** Every v0.13 selftest vector has an immutable ID and expected value. New tests may be added, but existing ones cannot change.
2. **Diff review for numerical constants.** Any change to material properties, IPC-2221 k factors, conventions, or tolerance checks requires session-authorized justification.
3. **Regression test suite.** Runs before every merge. Covers all three selftest domains (headless, reference board, real board).
4. **Manual integration gate.** Only the session coordinator marks work "INTEGRATED." Previous sessions are protected.
5. **Documented deviations.** Session handoffs explicitly list any intentional breaks and their justification.

---

## Permitted Changes Within Sessions

✓ **Code reorganization:** Move functions into modules, rename internal functions, split files  
✓ **Internal optimization:** Faster pathfinding, reduced memory, caching (if results preserved)  
✓ **Bug fixes:** Correct known issues (with regression test to prevent recurrence)  
✓ **Test coverage improvement:** Add new unit/integration tests  
✓ **Documentation:** Clarify existing behavior, update CLAUDE.md, add type hints  
✓ **UI polish:** Better spacing, clearer labels, improved help (no workflow change)  
✓ **Schema extensions:** Add optional fields (v0.13 files must still load)  

---

## Forbidden Changes Within Sessions (Without Coordinator Approval)

✗ **Numerical behavior outside tolerance** (without proof)  
✗ **Breaking CLI syntax** (e.g., rename --plating to --plate)  
✗ **Removal of validated vectors** (v0.13 tests may be deprecated with replacement proof)  
✗ **Silent model changes** (e.g., simplify via resistance without explicit authorization)  
✗ **Schema breaking changes** (v0.13 files must load)  
✗ **Worktree deletions** or shared-branch rewrites  

---

## Session Discipline

Each session:
1. **Owns a clear scope.** Defined punch-list items and affected paths.
2. **Records the baseline commit.** Can be reverted if parity breaks.
3. **Runs pre-change tests.** Confirms v0.13 baseline is passing.
4. **Makes coherent changes.** One logical extraction or integration per session.
5. **Runs post-change tests.** Confirms all acceptance vectors still pass.
6. **Documents deviations.** Lists any intentional breaks in the handoff.
7. **Produces a handoff.** Details changes, decisions, test results, and next steps.

---

## Remediation

If a session breaks parity unexpectedly:

1. **Detect immediately.** Regression test fails, acceptance vector breaks, or reported by team.
2. **Isolate the commit.** Revert the session's changes to confirmed-working state.
3. **Root-cause analysis.** Determine which code change caused the break.
4. **Option A: Fix forward.** Add a regression test and fix the code correctly.
5. **Option B: Revert session.** Await coordinator guidance; plan a repair session.
6. **Document the incident.** Update handoff with findings and resolution.

If multiple sessions break parity simultaneously, the coordinator may:
- Request simultaneous repair
- Revert to a known-good state
- Extend a session to include fixes

---

## Approval and Evolution

**ADR-001 is approved for implementation through M1 (Package split).**

Session coordinators may extend or modify this policy:
- Before M1 checkpoint: Iteratively with team feedback
- After M1: Only with written amendment; all sessions must follow the established pattern

This ADR may be superseded by ADR-002+ if the project decides to move to phase-based releases or other governance.

---

## Consequences

| Consequence | Severity | Mitigation |
|---|---|---|
| Slower initial refactor pace | Medium | Worth it for confidence and team adoption |
| More test infrastructure needed | Medium | Builds on v0.13 acceptance suite; payoff is early regression detection |
| Session scope discipline required | Medium | Clear punch-list items; coordinator review catches scope creep |
| Merged histories cannot be squashed | Low | Use linear history; helps blame and bisect |
| Diff reviews take longer | Medium | Clear scope + parity focus makes reviews fast |
